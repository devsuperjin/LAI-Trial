# 上游同步

[English](upstream-sync.md)

## 概要

生产依赖固定到精确的 DSH 版本。升级在独立集成分支进行，在新版本验收前保留上一个应用提交、锁文件与数据备份。

## 目录

- [升级](#升级)
- [兼容性 CI](#兼容性-ci)
- [回滚](#回滚)

## 升级

从已验收的应用分支创建 `integration/dsh-<精确版本>`。审阅官方发布说明、包导出、Profile 配置、会话格式与存储迁移。通过 `node scripts/set-dsh-version.mjs <精确版本>` 统一修改 DSH 依赖，再执行 `pnpm install --no-frozen-lockfile` 生成新锁文件。如果该版本要求调整 Cordis Peer，也需明确更新。

版本脚本切换版本时会清空旧的上游提交，需要将审阅过的候选提交写入 `config/dsh-baseline.json`。适配方法与使用者同步更新。合并前执行 `pnpm check`、Broker 集成测试、带认证前后端检查和真实模型任务场景。这些是维护流程，不代表候选升级已经通过。

## 兼容性 CI

`.github/workflows/compatibility.yml` 在推送与 PR 上运行生产基线。手动运行时填写精确 `candidate`，会在独立检出中额外检查候选版本。两组检查都使用 Redis、RabbitMQ 与 MQTT，构建全部自有包，并运行协议、生命周期及配置组合测试。CI 缺少 Broker 时直接失败，不跳过测试。

不自动追踪上游默认分支源码，升级候选需明确选择已发布版本。真实模型调用与生产界面验收仍属于需要凭据的集成工作。首次本地迁移在用户要求改名前已通过构建、前端类型检查与 42 项测试；6 项 Broker 测试因服务不可用跳过。不宣称后续验证已运行。

## 回滚

保留上一发布提交与锁文件，使用该提交的干净检出，按冻结锁文件安装并重新构建。尝试新版本前备份 `.runtime/dsh`。若升级更改了持久化数据，应在停服后将配套的升级前备份恢复到隔离主目录，不能假设旧 DSH 能读取新会话代次。不删除或重写用户原来的 DSH 主目录。

每个应用插件拥有独立语义化版本与包导出。独立发布前需要审阅 `pnpm pack` 内容；源码导出或相对源码路径不是运行时分发方式。首次迁移没有需要重新应用的框架补丁。
